**Paste a YouTube link. Get a note with the whole transcript in it, timestamped, in your folder, under your frontmatter conventions. That's the entire product.**

## Why care?

A lot of the best thinking in any field is spoken now — the two-hour podcast, the conference talk, the founder interview someone posted on a Tuesday. To a vault built on text, all of it is a dead URL. You can't search it. You can't link to a claim inside it. You can't quote it without scrubbing a timeline by hand and typing what you hear.

Stenographer makes spoken sources behave like every other note you own. One command, one link, and the words are *in your vault* — in your folder structure, under your frontmatter keys. From that moment it's ordinary material: backlinks work, search works, tags work, Dataview works, your own plugins work.

The part we're most pleased with is what the transcript is written *as*. It's a Lossless Flavored Markdown `:::transcript` block, which means the same file reads as clean plain markdown in any editor **and** hydrates into an interactive, timestamp-linked player when you publish it through an Astro Knots site. One artifact, two lives, no export step in between.

## What you get

```yaml
---
title: "Oh-My-Pi: Is This The Best Agent Harness?!"
youtube_url: "https://youtu.be/jcCPUcS4yzs"
channel: "NeuralNine"
date_published: "2026-08-03"
duration_seconds: 1193
transcript_engine: "supadata"
---
```

```markdown
:::transcript
[00:00] Today we're going to take a look at Oh-My-Pi, which is a coding agent
built on top of the Pi harness…

[00:09] …but this one follows an entirely different design philosophy.
:::
```

Note the frontmatter key: **`youtube_url`**, not a generic `source`. An Apple Podcasts link writes `apple_podcasts_url`, SoundCloud writes `soundcloud_url`, Vimeo writes `vimeo_url`, and so on down a list of a dozen platforms. Vaults refer to sources by where they came from, so the plugin does too. Unrecognized hosts fall back to a configurable generic key, and the whole behavior has an off switch.

## Two commands

- **Generate transcript from URL** — opens a modal, you paste a link.
- **Generate transcript from the URL under the cursor** — reads the link out of your selection, or just the line the cursor is sitting on.

Both land in the same modal, so there's exactly one place a transcription gets configured.

## Bring your own key

Stenographer never bills you through us. You add a provider key in settings and it's sent only to that provider.

| Provider | Handles | Free tier |
|---|---|---|
| **[Supadata](https://supadata.ai/)** — start here | YouTube, TikTok, Instagram, X, Facebook | 100 requests/month, no credit card |
| **[AssemblyAI](https://www.assemblyai.com/)** — optional | Direct audio files, **plus speaker labels** | $50 credit, no credit card |

The cost detail worth knowing: on Supadata, reusing a video's **existing captions costs 1 credit**, while *generating* a fresh transcript costs **2 credits per minute**. So a captioned video is 1 credit — your free 100/month is 100 videos — but a caption-less hour is 120 credits. That's what the `native` / `generate` / `auto` mode setting controls, and it ships defaulted to `auto`: reuse captions when they exist, generate only when they don't.

## Why there are two engines

This is the one design decision worth explaining, because it looks arbitrary until you hit the constraint.

**AssemblyAI, Deepgram, and ElevenLabs will not ingest a YouTube page.** They need a direct media URL. Producing one from YouTube means running `yt-dlp` somewhere — which means either shipping a Python dependency to every user or standing up a server. Stenographer v1 does neither, on purpose: a plugin that requires infrastructure ships after the infrastructure does.

Supadata ingests the platform URL itself. So it isn't a preference, it's the only path to YouTube without a server. AssemblyAI earns the other half of the split honestly — it's the only engine here that knows *who* is speaking, so direct audio links route to it and come back diarized.

The routing rule lives in exactly one function, and **the modal shows you its verdict before you spend a credit** — `youtube → supadata`, `direct media → assemblyai`. A constraint that's invisible until it fails is a constraint that should be printed on the screen.

## Details that took the most thought

**Caption tracks arrive as confetti.** YouTube hands back 2–5 word fragments. One timestamped line per fragment is a wall nobody will read. Fragments now merge up to a configurable character budget — but **a speaker change always breaks the line**, however short, because collapsing a diarization boundary to save whitespace destroys real information.

**Nothing overwrites.** A transcript can represent minutes of paid API time. Filename collisions resolve by appending ` 2`, ` 3` — Obsidian's own convention — never by clobbering.

**Failures are ranked by what they cost you.** Metadata is fetched first because it names the file, but a metadata failure returns null and the run continues: losing a title is annoying, discarding a transcript you already paid for is not. An empty transcript stops the run loudly instead of leaving a hollow note behind.

**Your tags stay yours.** Providers return tags, and they're SEO keywords chosen by an uploader — not vocabulary from a namespace you curate by hand. Off by default, with a toggle for anyone who wants them.

**Symlinked folders work.** Obsidian's index doesn't reliably contain symlinked directories, and plenty of vaults alias folders in from a repo. The usual "index says missing, so create it" idiom would hit a real directory, throw, and lose your transcript *after* the paid API call. Existence is checked against the filesystem too.

## Verify what you install

Every release asset is cryptographically attested back to the source commit and the GitHub Actions run that built it:

```bash
gh attestation verify main.js --repo lossless-group/stenographer
```

Exit 0 means the bytes in your vault really were built from the code you can read. There's no local `gh release create` path — releases only come out of the workflow.

## Known boundaries

Named here so the edges are honest rather than discovered:

- **Zoom recordings** aren't supported yet. Local Zoom files are a file-picker path and cloud recordings need OAuth — neither fits a paste-a-link surface. It's the top of the v2 list.
- **Apple Podcasts / Spotify page URLs** get the right frontmatter key but can't be transcribed — neither engine ingests those pages. Use the direct file URL from the show's RSS `<enclosure>`. Resolving that automatically is a small, obvious next step.
- **No streaming.** The note is created once the transcript is complete; neither provider's REST surface streams partial transcripts for pre-recorded media.
- **No playlists or channels** yet.
- **Desktop only** for now — nothing in the code requires it, it's just untested on mobile.

## Under the hood

- `src/utils/urls.ts` — platform detection and engine routing, plus a deliberately **separate** table for frontmatter key naming. Routing may only contain hosts Supadata can ingest; naming can safely recognize Apple Podcasts and Spotify. Merging them would route a link to an engine that rejects it.
- `src/services/supadataService.ts` — handles the synchronous 200 and the asynchronous 202-plus-polling paths transparently. Anything over ~20 minutes comes back as a job.
- `src/services/assemblyAiService.ts` — submit and poll, preferring utterances over words since they arrive already grouped by speaker turn.
- `src/transcript/lfm.ts` — `:::transcript` rendering, `[HH:MM:SS]` formatting, segment grouping.
- `src/services/pipeline.ts` — the one path from a URL to a note in the vault.

Both provider contracts were verified against live documentation rather than written from memory, which caught a real discrepancy: AssemblyAI's API-reference page documents `Authorization: Bearer <key>` while its speech-to-text guide specifies the raw key with no prefix. The guide is correct.
